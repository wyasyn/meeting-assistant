# 09 — Decisions and open questions

Append-only log. Format: `ADR-NNN — date — title`, then context, decision, consequences (3–6 lines total).

## ADR-001 — 2026-10-02 — Modular monolith desktop app
Single-user, single-machine product. Microservices add hops and failure points with no gain. Decision: one Tauri app with internal modules behind traits + one Python sidecar for local ML. Revisit only for a future sync backend.

## ADR-002 — 2026-10-02 — Tauri 2 + React/TS over Electron and Flutter
Electron fails the idle-RAM target (NFR-1); Flutter desktop is weak for Linux system-audio capture. Rust is limited to core modules; most code stays in TypeScript and Python.

## ADR-003 — 2026-10-02 — Two-track capture; mic = "me"
Separate mic and system tracks make the user's identity certain without diarization and enable echo de-dup. Diarization runs only on the system track.

## ADR-004 — 2026-10-02 — Local-first with bring-your-own key
All data local and encrypted; the user selects a provider and supplies a key (Gemini first). No backend, no telemetry. Offline mode via Whisper + Ollama later.

## ADR-005 — 2026-10-02 — Deterministic metrics + LLM judgement for scores
Metrics computed in code keep scores consistent and explainable; LLM covers qualitative parts and must cite segment IDs.

## ADR-006 — 2026-10-02 — SQLite (SQLCipher, FTS5, sqlite-vec)
One encrypted file, fast local search, no server. UUID v7 + timestamps keep it sync-ready.

## ADR-007 (2026-10-02): React 19 + Tailwind v4 instead of React 18
The stack named React 18, but current shadcn/ui targets React 19 and Tailwind v4, and new components assume them. Decision: scaffold with React 19, Tailwind v4 (`@tailwindcss/vite`, no `tailwind.config`) and shadcn's `cn` package in place of clsx + tailwind-merge. TypeScript 6 deprecates `baseUrl`, so the `@/*` alias uses `paths` only.

## ADR-008 (2026-10-02): Placeholder name and bundle identifier
The product name is still open. Decision: `productName` "Meeting Assistant", identifier `dev.meetingassistant.app`, Rust crate `meeting-assistant` (lib `meeting_assistant_lib`). UI reads `APP_NAME` from `app/src/config.ts`. Change all four together once a name is chosen; the identifier must be final before the first public release because it sets data and keychain paths.

## ADR-009 (2026-10-02): Lint and test tooling
Frontend: ESLint 10 flat config with typescript-eslint `strictTypeChecked` + `stylisticTypeChecked`, react-hooks and react-refresh; `no-explicit-any` is an error. Prettier (with `prettier-plugin-tailwindcss` for class order) runs inside `npm run lint`. Vitest + jsdom + Testing Library, coverage via `@vitest/coverage-v8` (NFR-23). Rust: clippy denies `unwrap_used` and `expect_used` through `[lints.clippy]` in Cargo.toml, with `clippy.toml` allowing them in tests, so the AGENTS.md rule is enforced rather than reviewed. Python: ruff rule sets E, W, F, I, B, UP, SIM, and `ruff format --check` is part of the lint command.

## ADR-010 (2026-10-02): Error shape and logging
`AppError` (thiserror) serialises to the contract `{ code, message, retryable }`; a new `internal` code covers failures with no contract code, shows a generic message and logs the detail at debug only (rule 8). Retryable codes: `provider_unavailable`, `invalid_llm_output`, `sidecar_down`. Logs: `tracing-subscriber` with a daily rolling file in `<app_data>/logs/` (7 files kept), stderr in debug builds, default filter `info` overridable by `RUST_LOG`, panics logged by a hook. The UI calls commands only through `call`/`on` in `lib/ipc.ts`, which always reject with an `AppError` instance.

## ADR-011 (2026-10-02): Store encryption, key handling and migrations
`rusqlite` with `bundled-sqlcipher-vendored-openssl`, so every OS builds the same SQLCipher with no system OpenSSL. The key is 32 random bytes (`getrandom`) stored as a binary secret in the OS keychain via `keyring` 4 (service = bundle identifier, account `db-key`; Secret Service over zbus on Linux, no extra system package) and passed as a raw hex key, so there is no passphrase derivation. If the database exists but the key is gone, opening fails with a readable storage error and no new key is made, since that would lock the data out for good. Migrations use a small in-house runner (`include_str!` + `PRAGMA user_version`, one transaction per file) instead of a crate. The connection sits behind a `Mutex` in Tauri state until the job queue needs a pool.

## ADR-012 (2026-10-02): Tray-resident app and start on login
Closing the main window hides it; the app keeps running in the tray so detection can work in the background, and Quit in the tray menu exits. The window starts hidden and is shown in setup unless the process got `--minimized`, which only the login item passes (FR-8.5). Start on login uses `tauri-plugin-autostart`, and the OS login item is the source of truth (no copy in `settings`), so it cannot drift if the user removes it outside the app. `tauri-plugin-single-instance` makes a second launch show the running window instead of opening the encrypted database twice. "Start recording" is in the tray menu but disabled until recording exists (roadmap 1.3). On GNOME the tray needs the AppIndicator extension (Fedora: `gnome-shell-extension-appindicator`); without it a second launch still brings the window back.

## ADR-013 (2026-10-02): PipeWire capture design and spike findings
Design: `AudioBackend` trait in `capture/` with a Linux `PipeWireBackend` (`pipewire` 0.10, Linux-only dependency; other OSes return "unsupported" until their backends land). Each capture owns one thread with its own main loop and two streams: mic (`media.role=Communication`) and system (`stream.capture.sink=true`, the output's monitor). Callbacks run on that thread, not the realtime thread, and push 48 kHz mono f32 frames into a bounded queue, dropping (with a warning) rather than blocking. Frames carry a per-track sample offset from session start.
Spike on Fedora 44, PipeWire 1.6.9, WirePlumber 0.5.18 (`examples/capture_spike.rs`):
- Requesting F32LE/48 kHz/mono works; the adapter resamples and downmixes, also for Bluetooth HFP.
- An idle output still delivers zeros on its monitor, so silence is not a gap.
- Streams without `target.object` follow a change of default output mid-capture (brief pause, then resumes).
- Built-in devices: both tracks complete, equal length.
- Bluetooth headset already in the headset (HFP) profile: both tracks complete.
- Bluetooth headset in A2DP when capture starts: opening the mic makes WirePlumber switch to HFP and both streams stall for seconds while still linked and "running". `pw-record` shows the same, so it is system behaviour, not ours.
Consequences: the track clock jumps offsets forward to wall-clock time on gaps over 100 ms, so tracks stay aligned and later steps can fill silence; a watchdog reconnects a stream with no data for 2 s (it recovered the mic in 3 of 4 runs; the system track can stay silent until the headset settles). In real calls the meeting app usually holds the mic first, so HFP is already active. The recording UI (1.3) must show live levels so a stall is visible. Not tested: a Bluetooth device disconnecting mid-capture.

## ADR-014 (2026-10-02): Encrypted 10 s Opus chunks and crash recovery
Each track is cut into 10 s chunks on a fixed timeline (chunk N starts at (N-1) x 10 s), with capture gaps encoded as silence so mic and system stay aligned and the pipeline can derive times from the index. Every chunk is its own Ogg Opus stream: the encoder is reset per chunk and flushed with one silent frame, and the last granule position trims the padding, so a chunk decodes and plays alone and can be sent to a provider as a standard file. We feed 48 kHz and cap the encoder at wideband (16 kHz audio, VOIP mode, 24 kbps, DTX), so libopus resamples and silence costs a few hundred bytes. libopus comes from the `opus` crate, built from bundled source with cmake, so no system package is needed on any OS. Chunks are sealed with AES-256-GCM using the database key (docs/04), a random nonce per file and `<meeting_id>/<track>/<N>` as associated data so files cannot be swapped. Writes go to `.tmp`, are synced and renamed, so a crash loses at most the chunk in progress: a `kill -9` at 17 s on Fedora kept the first 10 s of both tracks intact. At startup, meetings still in `recording` become the new `interrupted` status (no migration: the column has no CHECK), their audio is kept and their length is read from the last chunk. The audio dir is stored relative to `<app_data>` so moving the data folder keeps it valid. Fedora check: built-in devices gave complete, aligned tracks with a test tone continuous across chunk boundaries; the Bluetooth headset still stalls as in ADR-013, and those gaps are saved as silence.

## ADR-015 (2026-10-02): Manual recording controls, pause and the indicator
A `RecordingService` owns the one active recording and is the only way to start one: the window button and the tray menu call it; nothing else does (rule 1). Pause closes the capture session so the devices are released and the OS mic indicator turns off; resume opens a new session and continues both tracks from the end of the longer one, so paused time is not stored and the tracks stay aligned (the shorter one is padded with silence). `elapsedMs` therefore counts recorded time only. Stop flushes the last chunks and sets the meeting to `processing` for the job queue (1.7). A watchdog checks the recorder every 500 ms; if capture or saving died by itself the meeting becomes `interrupted` (audio kept) and `recording:state` carries a readable `error`. Quitting from the tray saves a running recording first. Levels are RMS per track over 100 ms, `null` when a device sent nothing, so a stalled Bluetooth track (ADR-013) is visible rather than looking silent. The tray shows the state with a red dot painted onto the app icon at runtime (grey while paused, no extra asset), the label "Recording" or "Paused" next to it on Linux, and Start/Stop and Pause/Resume menu items; the window shows the same red dot and label in a bar fixed to the top. Device choice and the FR-1.4 global hotkey come later (FR-8.3 settings). Commands run on a blocking worker so device setup and file flushing never stall the UI thread. Tray-started recordings are titled "Recording"; the window passes a local-time title.

## ADR-016 (2026-10-02): Detector v1, process watch plus mic streams
Detection only emits `meeting:detected`; it never starts a recording (rule 1). Processes come from `sysinfo` (names and pids only, no threads) every 3 s, so Windows and macOS reuse it later. On Linux a registry watch on its own PipeWire thread reports `Stream/Input/Audio` nodes; registry globals carry no owner, so each stream node is bound once and its info gives `application.process.binary` and `application.process.id` (set for native and PulseAudio clients). Rules live in a pure `Engine` fed timestamps: a desktop app holding the mic 3 s is a meeting (0.9 confidence with its process seen, 0.7 when only the stream names it, e.g. Flatpak), a browser needs 10 s (0.5) to skip voice search and mic tests. One signal per app per meeting: it re-arms after 60 s without the mic, so mute toggles and device switches do not prompt twice. While recording or paused nothing is signalled and apps holding the mic count as signalled, so stopping mid-call does not prompt. Our own capture streams are ignored by pid. If PipeWire goes away the watch ends, streams are forgotten and it retries every 10 s. Other OSes have no stream watch yet, so no detection there. `title` is null (Wayland hides window titles); signals are not stored until the 1.5 prompt needs them. `browser` is a new `source_app` value.

## ADR-017 (2026-10-02): Consent prompt and per-app rules
Every detection goes through a `ConsentService` before the user sees it: `never` drops it, `always` starts recording at once (the stored rule is the user's action, rule 1) and `ask`, the default for an app with no row, shows the prompt. The prompt appears twice: as an OS notification with Record / Not now / Never for <app>, and as `meeting:detected` for a banner in the window. Whichever is answered first wins and the other closes (`meeting:prompt-closed`). A recording starting by any route closes every open prompt, and a newer detection of the same app replaces its unanswered prompt. Dismissing the notification leaves the window banner, which goes away with Not now, a recording or the next detection. Not now in the window only closes the banner; the notification stays until the desktop clears it. Tauri's notification plugin has no action buttons on desktop, so Linux uses `notify-rust` 4 (pure Rust over `org.freedesktop.Notifications`, zbus 5 already in the tree via `keyring`), a Linux-only dependency behind a `Notifier` trait. Prompts never expire; clicking the notification body opens the window. Other OSes have no detection yet (ADR-016) and get a no-op notifier, so only the window prompts there for now. An `always` start shows a "Recording" notification with a Stop button, closed when the recording ends; if that start fails, the user is asked instead. A failed Record from a notification shows a "Could not record" notification with the reason. Recordings from a prompt are titled "<App> meeting" by the core. Rules are set from the prompt (Never) or a list in the window (Always ask / Always record / Never record); no schema change, `app_rules` was in `0001`.

## ADR-018 (2026-10-02): End of meeting and the stop prompt
End detection never stops a recording: it asks "Meeting over?" with Stop recording / Keep recording, as a notification and as a window banner, through the consent service like the start prompt (`meeting:ended`, closed by `meeting:prompt-closed`). Three signals, all only while recording or paused. App closed: the watched app's process was seen during the recording and is gone from the 3 s scan. Mic released: the watched app has held no mic stream for 30 s; the grace covers mute toggles and device switches that close the stream, and it is the only signal for browsers (they stay open) and Flatpak apps (process hidden). The recording's own app is watched; a recording started by hand has no app, so every known app that holds the mic during it is watched. Silence: the recorder's level feed (RMS per 100 ms) with both tracks under -50 dBFS, or no audio from a device, for 2 minutes. A gap of over 1 s between level updates is a pause, so paused time never counts as quiet. Each signal fires once per stretch and re-arms when the app holds the mic again or sound returns. One end prompt at a time: a newer one replaces it, and stopping the recording closes it; Keep recording in the window only closes the banner, as with Not now (ADR-017). The silence report runs on its own worker, because the recorder thread calls it and a pause may hold the recording lock while waiting for that thread. The thresholds are first guesses to tune on real calls. `meeting:ended` was listed with `{ meetingId }`; it now carries `signalId`, `sourceApp` and `reason` too.

## ADR-019 (2026-10-02): Job queue
The queue is the `jobs` table (no schema change) and one `jobs` worker thread instead of a tokio worker pool: steps run one at a time and in order, so a meeting never has two steps racing and the CPU stays free for recording. Steps are a `StepRunner` trait that may block; async provider calls (1.8) run inside them with the Tauri runtime's `block_on`. One row per meeting step: finishing a step queues the next, and the last step sets the meeting `ready`. Errors marked retryable in `AppError` (`provider_unavailable`, `invalid_llm_output`, `sidecar_down`) are retried after 30 s, 2 min, 8 min, 32 min, then 1 h (6 attempts in all, about 1 h 40 min). Any other error, or the 6th failure, marks the job and the meeting `failed` with a readable error. Audio is never touched, so `reprocess` (FR-4.6) can run it again later (NFR-7). Crash safety: a job left `running` is queued again at startup, since steps must be idempotent. The worker also queues the first step for any `processing` meeting without jobs, so a stop is picked up even if the app quits before queueing, and stopping only wakes the worker. Quitting does not wait for a running step; it is redone at the next start. The pipeline is empty until the transcribe steps land (1.8, 1.9), so stopped meetings wait in `processing` rather than being marked ready without a transcript. `job:progress` is emitted for every attempt start, success, scheduled retry and final failure.

## ADR-020 (2026-10-02): Provider trait and Gemini
`providers/` holds the `Provider` trait (async via `async-trait`, so jobs can hold `dyn Provider`), a `ProviderService` that keeps one keychain entry per provider and builds providers from it, and the Gemini implementation, the only code that knows Gemini's wire format (rule 7). New dependencies: `reqwest` 0.13 (rustls with the OS certificate store, no system OpenSSL), `async-trait`, `base64`. Models: Gemini 2.5 is closed to new users, so transcription uses `gemini-3.5-flash-lite` (most of the tokens, about $0.08 for an hour of audio) and analysis `gemini-3.8-flash` (better reasoning; its price doubles on 2027-01-01). Both are constants in `providers/gemini`. The dedicated `gemini-3.5-transcribe` model was left out: it costs more, caps diarization at 30 minutes and its documented request format is inconsistent; revisit with a real key. Audio goes inline as base64, one part per 10 s chunk labelled with its number, and the model returns each utterance's chunk and offset, so times are mapped to the meeting in Rust instead of trusting the model's clock. Requests carry up to 180 chunks (30 minutes) or 14 MB of audio, under the 20 MB inline limit; speaker labels can differ between batches of a longer meeting, which the merge step (1.9) must handle. Output is constrained by `responseSchema` and parsed into typed structs; a malformed answer is rejected whole (`invalid_llm_output`, retried by the queue). The analysis prompt is a placeholder until 2.2, which also adds the segment id check. "Test key" looks up both models (free) and reports what Google said as readable text; Google's own error text goes to the debug log only. The key travels in the `x-goog-api-key` header, never the URL. A new command, `list_providers`, tells the settings screen whether a key is saved without reading it out.

## ADR-021 (2026-10-02): Transcribe and merge steps
The pipeline now runs `transcribe_mic`, `transcribe_system` and `merge`; after `merge` the meeting is `ready` (metrics and analysis join in Phase 2). A transcribe step lists the track's finished chunk files, decrypts them in memory and hands the bytes to the provider, so plain audio never touches the disk (the provider request carries bytes, not temp file paths). A track with no chunks stores nothing and needs no key. Results go straight into `segments` with their `track`, in one transaction that first removes the track's earlier segments and speakers, so a rerun or a crash mid-step is safe; renamed speakers of that track are lost on a rerun. The mic track is the user (rule 4): one `Me` speaker with `is_me`, never diarized. The system track is diarized; Gemini numbers voices per request, so each 30 min batch continues the numbering ("Speaker 1" of batch 2 becomes "Speaker 4" after three) rather than trusting labels across batches: one label never covers two people, and duplicates are fixed by renaming (1.10). Unlabelled system segments have no speaker. `merge` deletes mic segments that echo the other side (no headphones): system speech overlaps them within 300 ms and holds at least 60% of their words (lowercase letters and digits); ordering needs no work since segments are read by `start_ms`. Both thresholds are first guesses to tune on real calls. A missing API key does not fail the meeting: the job is parked (queued with no run time, the attempt uncounted, the reason in `job:progress`), and saving a key, or the next app start, releases it. Interrupted meetings are not queued yet; they wait for `reprocess` (FR-4.6). FR-3.1 is partial: segments are timestamped but `words` stays empty until a provider with word timings.

## ADR-022 (2026-10-02): Transcript view, playback and speaker rename
A `MeetingService` reads meetings back for the window: `list_meetings` (newest first, cursor `<startedAt>:<id>`, only `cursor` and `limit` for now), `get_meeting` (meeting, speakers, segments and `hasAudio`) and `rename_speaker`. The window shows the 20 most recent meetings under the recording controls and reloads on `recording:state` and `job:progress`; only `ready` meetings open. The full library with filters and scores is 2.5. Playback (FR-3.8): `get_segment_audio` decrypts the chunks under the line, decodes them at 16 kHz mono (the chunks are wideband, so nothing is lost and the file is a third of 48 kHz) and returns a WAV file as raw IPC bytes; the window plays it from a Blob URL. Plain audio stays in memory (ADR-021), no file path or custom protocol is exposed, and WAV needs no Ogg demuxing in WebKitGTK. A line plays its own track only, since mixing would double the voice when the mic picked up the speakers; missing chunks play as silence and one request is capped at 10 minutes. Rename (FR-3.3): the label is on the speaker, so every line follows. Giving a speaker the name of another speaker on the same side (ignoring case) merges them: lines move over and the renamed speaker is deleted. This is how a voice split across 30 min batches (ADR-021) is joined, and it keeps per-speaker metrics (2.1) right. "Me" never merges with the other side. Names are trimmed, 1 to 100 characters. `personId` waits for FR-3.4. No schema change.

## ADR-023 (2026-10-02): Deterministic metrics
`metrics::compute` is a pure function of the stored segments and the meeting's timing (`duration_s`, `scheduled_duration_s`), so it is tested with hand-built segments and needs no database. "Me" is the mic track (rule 4). Readings of `07-scoring.md` where it was loose: talk metrics use segments with a speaker; unlabelled system speech (ADR-021) still counts as speech for silence and as a question. `talk_share_<speaker>` is keyed by speaker id, so renames keep it. `balance` is 1 minus the Gini of talk time scaled by n/(n-1), so one voice holding all the time gives 0 instead of 0.5 (two speakers) and a 75/25 split gives 0.5; with fewer than two speakers it is undefined. An interruption is a speaker change that starts more than 300 ms before the previous segment ends, read as "overlaps it by more than 300 ms" (the literal "<300 ms before" would count polite handovers); only interruptions between me and others are counted, and short backchannels ("mm-hm") count too until real calls say otherwise. A monologue runs from a speaker's first segment to their last before someone else speaks, pauses included. Questions are segments ending in `?` or starting with a wh-word or "how" (contractions like "what's" included); auxiliaries such as "can" or "do" are left out because they start too many statements. Words are whitespace-split, lowercased and stripped of surrounding punctuation; two-word fillers never span segments, and "like" always counts, as the spec lists it. Silence is the total of gaps over 3 s with nobody talking, including before the first and after the last segment. `overrun_pct` is a percent and negative when the meeting ended early. A metric that is undefined (nobody spoke, no calendar, unknown length) is `None` and is not stored. `action_items_count` and `decisions_count` come from the analysis and are stored with the scores (2.3).

## ADR-024 (2026-10-02): Analysis prompt, cited lines and the metrics and analyze steps
The pipeline now runs `metrics` and `analyze` after `merge`. `metrics` stores every defined metric as a `metric:*` score with `{}` evidence and replaces its own rows on a rerun. `analyze` recomputes the metrics (pure and cheap, so it never reads stale rows), sends the transcript, the metrics and the template to the provider and saves the report, the action items and the analysis metrics (`action_items_count`, `decisions_count`) in one transaction that replaces the earlier ones; marking an item done is therefore lost on a rerun until FR-6.5 needs otherwise. The prompt lives in `providers/prompt.rs` so Gemini and the later Ollama provider send the same rules: only what the transcript says, no generic advice, never judge other people one by one, the language of the meeting, the metrics as facts, 50 as an ordinary meeting. Lines are cited by short refs (`s1`, `s2`, ... in time order) instead of 36-character UUIDs: about 10 fewer tokens per line and fewer mangled ids; the step maps them back before saving and any ref it does not know rejects the whole answer as `invalid_llm_output`, which the queue retries with backoff (ADR-019). The user is always "Me" in the prompt, even after a rename, so action item owners say "Me". Small slips that are not schema errors are dropped instead of burning a retry: a due date that is not YYYY-MM-DD, a blank owner or task, a chapter outside the meeting. A meeting with no segments is not sent and gets no report. `Provider::analysis_model` (default: the provider id) fills `reports.model_used`. Highlights join the prompt with FR-9.1 (2.7) and the cost with FR-8.4 (2.7).

## ADR-025 (2026-10-02): Score combination
`metrics/scoring.rs` turns the metrics and the LLM's four judgements into the headline scores with the docs/07 weights, all in one `ScoringConfig` (`DEFAULT_CONFIG`). docs/07 left most band edges open; first guesses, to tune on real calls: turns 1 to 6 per minute, questions 2 to 12 per 10 minutes, fillers up to 2 per 100 words, my interruptions up to 1 per 30 minutes, outcomes (decisions plus action items) at least 3 per 30 minutes, each falling linearly to 0 at the edges listed in docs/07. Questions, interruptions and outcomes are rates over the meeting's length so long meetings are not rewarded for size. The `general` template, which every meeting has until templates (3.4), uses the fair share of the speakers heard (1/N) plus or minus 30% as the healthy talk ratio. "No calendar → re-weight to LLM" is applied to every part whose metric is undefined (no wpm or filler rate when I said nothing, no balance with one speaker), so the parts always add up to 1 and nothing scores 0 for a metric that does not exist. Scores are rounded to whole numbers. Evidence is `{ metrics, parts, segment_ids, rationale }`: `parts` (name, weight after re-weighting, 0 to 100 score) is an addition to the docs/05 shape so the report can show why without recomputing; `segment_ids` and `rationale` come from the matching LLM judgement. Insufficient data (under 5 minutes, or under 50 words on the system track) stores no headline scores at all, so the UI shows "insufficient data"; the report and the metrics are still saved. Action items with a blank task are not counted.

## ADR-026 (2026-10-02): Report view
A meeting opens in a `MeetingView` that loads `get_meeting` once and shows two tabs, Report (first) and Transcript, with Radix Tabs for keyboard and screen reader support. The report shows the summary, the four scores (each with a "Why" disclosure listing the LLM rationale, every weighted part with the metric behind it in words, and the cited lines), key points, decisions, action items (owner "Me" shown as "You", due dates in the local format), open questions, suggestions tagged with the score they would improve, and chapters. Sections with nothing in them are left out. Every cited line is a link that switches to the transcript and focuses that line, so FR-5.5's "tied to a transcript moment" is one click. Too little data shows "Not enough to score" with the rule instead of numbers (docs/07). The summary is shown as plain text with its line breaks; no Markdown renderer was added. `MeetingDetail` now carries `report`, `actionItems` and `scores` (headline only; the metric rows stay in the database as evidence). Ticking action items done (FR-6.5) waits for Phase 3.

## ADR-027 (2026-10-02): Meeting library
`list_meetings` returns `MeetingListItem`: the `MeetingSummary` fields (flattened, so the shape only grows) plus participants and headline score values without evidence. Participants are the speaker labels of the other side, so a renamed speaker shows by name; "Me" is implied. Per page that is two small indexed queries per meeting, fine for pages of 20 to 200 on SQLite; revisit with search (3.1) if it shows up. The window lists every meeting under the recording controls with date, length, source app (nothing for meetings started by hand), "with ..." participants and the four scores, 20 at a time with "Show more"; a reload after `recording:state` or `job:progress` keeps the pages already shown. The status of a meeting still being processed now reads "Processing", since analysis runs after transcription. Filters (`query`, `tag`, `sourceApp`, dates) join with search in Phase 3.
